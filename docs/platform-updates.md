# 各平台应用更新约定

更新日期：2026-10-21。当前支持 Web 和独立 macOS 应用；Mac 自动更新、iOS 和 Android 原生更新仍待实现。

## 平台边界

| 运行形态 | 更新方式 | 当前状态 |
| --- | --- | --- |
| Web：桌面、iOS / Android 浏览器、添加到主屏幕的 PWA | 检查站点新版资源，完整下载后自动启用并重新加载，保留手动入口 | 已有实现 |
| macOS 原生应用（macOS 14+） | 手动替换应用包，保留沙盒内设置与缓存 | 可本地构建运行；自动更新和正式签名／公证分发待接入 |
| iOS 原生客户端 | 检查已发布版本，提示用户前往 App Store 下载／更新 | 待实现；尚无 Apple 开发者账号，App ID、商店链接和查询配置暂留空 |
| Android 原生客户端 | 检查已发布版本，用户确认后下载 APK，再提示用户通过系统安装器安装更新 | 待实现；版本信息地址、APK 地址和下载／安装逻辑暂留空 |

**按应用运行形态分流，不能仅凭设备系统判断。** iPhone 上的 Safari、主屏幕 PWA 都属于 Web，继续使用网页更新；只有原生 iOS 安装包才走 App Store。Android 同理。Flutter 接入时先判断 Web 构建／能力，再区分原生平台，不能直接用设备平台或 User-Agent 把手机网页送入原生更新流程。

## 当前实现与后续接入点

- [BrowserClient](../lib/platform/browser_client.dart) 通过条件导入选择实现；[WebBrowserClient](../lib/platform/browser_client_web.dart) 调用 [web/platform.js](../web/platform.js) 中的 Service Worker 更新流程。
- Web 在打开页面、保持前台及恢复网络等时机检查更新；资源准备好后前台页面自动加载新版，后台页面返回时更新；保留手动更新流程和设置、计时。具体间隔、缓存和失败行为见 [README 缓存和更新策略](../README.md#缓存和更新策略)。
- macOS 初始化 [NativeRuntime](../lib/platform/native_runtime.dart) 后使用 [MacBrowserClient](../lib/platform/browser_client_native.dart)，接入实际全屏、常亮和本地持久化。原生设置页说明手动替换应用包，不显示浏览器更新按钮，且不报告虚假的“已是最新版”。
- 其他非 Web 平台和未初始化原生服务的测试使用 [MemoryBrowserClient](../lib/platform/browser_client_stub.dart)；它是占位实现，不能作为原生客户端已支持更新的依据。
- 新增原生客户端时，需要接入独立的平台更新实现及真实版本信息来源；页面更新入口按平台和能力展示。原生客户端不能复用浏览器的刷新、离线缓存或 Service Worker 安装方法来更新应用包。
- 当前保留原生更新逻辑为空，不增加安装权限、下载依赖或虚构商店／APK 地址。未配置或未实现时隐藏可执行的原生更新入口，不显示“已是最新版”来掩盖未接入状态。

## macOS 更新与分发边界

如需自行构建，使用 `bash tool/build_macos.sh` 生成 `.app`；应用版本、Info.plist 和首页版本文字统一读取 pubspec 的版本与构建号，独立于 Pages 部署序号。本地构建只做 ad-hoc 签名验证，不能替代 Developer ID、公证或 Gatekeeper 的正式分发验收。

更新时退出旧应用并替换应用包；相同 Bundle ID `com.kingxcode.timeNest` 保留原沙盒数据。Mac 当前没有下载、安装或检查新版的服务，不应复用 Web 刷新方法替换应用。后续接入自动更新时再确定正式签名、更新源、版本比较和失败恢复流程。

## iOS 原生客户端待实现

预期流程：读取本机应用版本 → 查询目标渠道已上架且可下载的版本 → 有新版时展示版本与更新说明 → 用户点击“前往 App Store” → 打开本应用的 App Store 页面，由用户在商店下载／更新。

- 有开发者账号并创建、发布应用后，再配置真实 App ID、App Store 链接和版本查询方式。查询来源与地区可用性需在接入时确定。
- 跳转商店本身不等于更新成功；下次进入应用时读取实际安装版本重新判断。
- 未配置、查询失败、商店无法打开或目标版本尚未上架时，不中断时钟和计时；提供适当提示或重试，不能跳转占位地址。
- 本项目选择 App Store 作为 iOS 原生更新渠道，不在应用内下载安装包替换自身。

App Store 产品页链接可在应用信息齐备后配置，参考 [Apple：推广应用与商店链接](https://developer.apple.com/app-store/promote/)。当前不填写假 App ID 或链接。

## Android 原生客户端待实现

预期流程：读取本机应用版本 → 查询已发布的 Android 版本信息 → 提示版本、更新说明和安装包大小 → 用户确认下载 → 展示进度并校验 APK → 调用系统安装界面 → 用户确认安装 → 再次启动时核对实际安装版本。

- 接入时确定版本信息发布地址、HTTPS APK 下载地址、包大小和校验值；发布信息必须与已上传且可用的安装包对应，不先发布指向不存在文件的更新提示。
- 下载完成不等于安装完成；取消、断网、下载失败、校验失败、空间不足、安装权限未授予及安装失败均需可恢复，不影响继续使用当前版本。
- 使用正式签名，保持应用包名及可升级的签名身份一致；校验下载完整性，并由系统验证安装包和升级资格。不能把测试签名包当成现有正式包的升级包。参考 [Android：应用签名](https://developer.android.com/studio/publish/app-signing)。
- 安装由系统和用户确认，不承诺静默安装；根据目标 Android 版本处理安装来源授权。参考 [Android：通过网站分发与安装来源授权](https://developer.android.com/distribute/marketing-tools/alternative-distribution)。正式接入时重新核对目标系统、分发渠道和地区的要求。
- APK 托管方式及权限申请代码当前均留空；若以后增加应用商店渠道，需要按渠道另行适配，不能把所有 Android 安装来源统一当作自分发 APK。

## 新增客户端的发布前检查清单

以下为待办，不能因为 Flutter 可以编译 iOS / Android 就视为完成。接入原生客户端时须逐项验收，并记录平台、系统版本、安装来源、旧／新应用版本和结果。

- [ ] 明确 Web / PWA、iOS 原生、Android 原生的更新分流；手机网页继续走 Web 更新。
- [ ] 接入实际安装版本读取和相应平台、渠道的已发布版本查询，明确版本号／构建号比较规则，不使用字符串大小比较或拿 Web 资源哈希比较原生版本。
- [ ] 区分未接入、检查中、无更新、有更新、失败等状态；没有配置时不显示无效按钮或虚假的“最新版”状态。
- [ ] iOS：真实 App Store 配置就绪；验证发现新版、商店跳转、无法打开商店、查询失败及更新后重新检查。
- [ ] Android：真实版本与 APK 地址就绪；验证下载进度、取消／重试、校验失败、安装来源授权、系统安装确认及安装后版本检查。
- [ ] 验证应用标识与签名兼容，旧版本能够覆盖升级；保留并迁移用户设置、进行中的计时和其他本地数据。
- [ ] 原生客户端检查更新不自动退出或重启当前展示；用户主动确认后才进入对应原生更新流程，忽略提示或更新失败仍可使用当前版本。Web 按上述自动更新策略执行。
- [ ] 验证多次点击、前后台切换和断网恢复不会重复下载、重复弹出安装界面或丢失状态。
- [ ] 回归 Web 的自动更新、手动刷新、离线缓存和多标签页更新；原生代码不引入 Web 不支持的依赖。
- [ ] 更新本文件的平台状态、README、构建／发布流程和真机验收记录；未完成的项目明确记录，不能宣称该客户端已具备完整更新能力。

## 手动检查进度（2026-10-28）

- Web 设置页检查按钮显示旋转指示与“检查更新中”，进行中禁用重复点击；状态由浏览器服务持有，关闭再打开设置不会丢失进度。
- 连接检查不提供百分比。发现安装中的新版后显示准备资源；离线资源项数只使用 Service Worker 实际上报的完成数/总数。
- 检查正常完成后区分当前最新和新版就绪；失败与超时明确提示可重试。不把尚在下载、离线失败或服务不可用解释为“最新”。
- 核查阶段上限 30 秒，资源准备阶段上限 90 秒；“最新”还需活动 worker 回应有效版本，4 秒内无回应按核查失败处理。离开页面取消本次提示，迟到结果不会覆盖后续请求。
- 此反馈不改变原生 macOS 的手动安装更新边界，也不自动清理用户数据。
